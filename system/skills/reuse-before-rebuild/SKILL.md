# 재사용 우선 — 판정 로직 재발명 금지

## ★★★ 핵심 사고 (2026-08-30, 가장 강하게 표시된 실례)

새 도구(`도구/audit_ledger_recurrence.py`)를 만들면서 원장을 파싱하는 로직을 새로
짰는데, **`도구/feedback_lookup.py`가 이미 오래전에 고쳐 둔 버그(표 형식과 산문
형식을 둘 다 읽어야 하는 것)를 그대로 다시 저질렀다** — 258개 행이 통째로 안
읽혔다. 코드 주석에 이미 *[발화 생략]*고 적혀 있었는데도
무시됐다. 고친 뒤엔 새 도구가 `feedback_lookup.rows()`를 **직접 재사용**하도록
리팩터해서 해결했다.

## 체크리스트 (새 코드를 짜기 전에)

1. **지금 읽으려는 파일 형식(원장·CSV·설정·로그)을 이미 다른 도구가 읽고 있는가?**
   `grep -l`로 그 파일 이름을 리포 안에서 검색해본다.
2. **있다면, 그 도구가 이미 겪었던 파싱 함정(형식이 두 가지다, 인코딩이 다르다,
   구분자 안에 구분자가 있다 등)이 코드 주석·docstring에 적혀 있는가?** 있으면 그
   경고를 무시하지 말고 그 함수를 직접 import해서 쓴다 — 로직을 다시 베끼지 않는다.
3. **같은 사실을 검사하는 코드가 두 벌 이상 생기고 있지 않은가?** ("자를 두 벌 두면
   갈라진다" — 이 저장소에서 6회 이상 재발한 부류). 두 벌이 필요해 보이면, 진짜
   이유가 있는지 아니면 그냥 몰라서 새로 짠 건지 스스로 확인한다.
4. 정말 기존 로직이 지금 필요와 안 맞으면(예: 다른 데이터 형식) — **그 사실을 명시적
   으로 적는다**("~와 다른 이유로 재사용 안 함") — 아무 설명 없이 새로 짜지 않는다.

## 검사기를 잴 때도 마찬가지 — 흉내 코드로 재지 않는다

출처: XSanity 세션 메모리 이관(2026-09-01). 검사기(체커·훅·게이트)가 실제로 어떻게
동작하는지 확인해야 할 때, 그 동작을 흉내 낸 별도 코드를 짜서 재는 것은 **재사용
원칙의 반대편에서 같은 실수를 낸다** — 진짜 자가 아니라 자기가 상상한 자를 재는
것이다. 두 번 틀린 뒤 확립된 습관이다.

체크: 검사기 동작을 확인하려는데 지금 짜려는 코드가 그 검사기 자체를 부르는가,
아니면 그 검사기가 "이렇게 동작할 것"이라는 가정을 새 코드로 재현하는가? 후자면
멈추고 **실제 검사기를 그 입력으로 직접 돌린다.**

## 왜 이게 훅이 아니라 Skill인가

특정 사고 하나는 리팩터로 기계적으로 막았지만, "새 코드 짜기 전에 기존 코드부터
찾아본다"는 습관 자체는 매번 다른 파일·다른 상황이라 규칙 하나로 못 박을 수 없다.
