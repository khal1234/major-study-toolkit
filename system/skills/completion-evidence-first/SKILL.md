# 완료 판정·보고 절차

가장 자주, 가장 오래 반복된 병("완료 과장")의 하위 절차다. 이 저장소들의 원장에서
2026-08-01부터 2026-08-16까지 두 달째 마찰 1위였고(`buggy_code`·`wrong_approach`는
높은데 `missed_instructions`는 거의 0 — 지시를 놓친 게 아니라 과잉이었다), 그 뒤로도
계속 변주된 형태로 재발했다. 이 Skill은 "다 됐다"를 선언하기 직전에 세 가지를 점검한다.

## ① 검증 기준이 사용자의 실제 요청 문장과 일치하는가 (존재확인 ≠ 발견가능성)

- 실사고(2026-08-27): 링크 21개를 페이지에 넣고 "링크 21개 일치"로 검증 통과시켰다.
  그런데 `text-decoration:none`이라 화면에 링크처럼 안 보였다. 사용자 요청 원문은
  "누르면서 확인"이었는데, 검증은 **존재**를 셌지 **누를 수 있는지**는 안 쟀다.
- 체크: 사용자가 쓴 동사를 그대로 검증 기준으로 옮겼는가? ([발화 생략]고 했으면 화면에서
  실제로 보이는지, "누른다"고 했으면 클릭 가능한지 — 그 동사가 요구하는 관측을 했는가.
- 이건 규칙으로 못 박기 어렵다(정상적인 비-밑줄 UI도 많아 오탐 위험) — 그래서 매번
  판단해야 하고, 그게 이 Skill이 필요한 이유다.

## ② 검증 주기와 발행(외부로 나가는 행위) 주기를 분리했는가

- 실사고(2026-08-27): 사용자가 여러 판정을 한 번에 요청했는데, 판정 하나 날 때마다
  매번 재발행(재커밋·재게시)했다. **로컬 검증은 싸니 매 단계 돌아도 되지만, 외부로
  나가는 발행(비싸고·시끄럽고·되돌리기 어려움)은 배치 전체가 끝났을 때 한 번**이어야
  한다.
- 체크: 지금 하려는 "완료 보고"·"커밋"·"게시"가 사용자가 실제로 요청한 배치 단위와
  일치하는가, 아니면 판정마다 쪼개서 나가고 있는가?

## ③ 사용자가 콕 집은 결함을 [발화 생략]으로 재포장하고 있지 않은가

- 실사고(2026-08-16): 사용자가 삽화 좌표가 틀렸다고 지적했는데, 세션이 [발화 생략]라며 대수적 근거를 대며 반박했다. 결국 그냥 고칠 문제였고, 사용자가 다시 짚어야
  했다.
- 체크: 사용자가 구체적 좌표·수치·글자를 지목했다면 그건 대개 **관측**이지 **판단**이
  아니다. "이게 왜 이런지 설명"하는 게 "고친다"를 대신하고 있지 않은지 스스로 되묻는다.
  진짜 설계 의도라면 그 근거를 먼저 보여주고 사용자 판정을 받는다(추측으로 방어하지
  않는다).

## 완료 선언 형식 (규칙/증거의-정직.md와 짝)

```
항목 · 증거 명령 · 실제 출력
```
명령을 못 대면 "완료"라고 쓰지 않는다 — "미검증"으로 열어 둔다. 부분만 봤으면 본 만큼의
분수를 그대로 적는다(반올림 금지).
